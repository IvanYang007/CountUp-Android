# Spec: Release Hardening, Data Integrity & Widget Resilience

## Problem Statement

Users rely on CountUp to track deeply personal, long-running milestones and habits over months and years without accounts or cloud lock-in. However, multiple edge-case failure modes currently put user data, privacy, and day-to-day reliability at risk:

1. **Catastrophic Data Loss via Corrupted Backups**: If a backup file is damaged, truncated, or generated by a newer version of the application, the app silently salvages partial tokens and treats the result as a normal backup. If a user selects "Replace All", their entire history of genuine counters is permanently obliterated and replaced with an incomplete salvage, with zero pre-restore rollback available.
2. **Blocked Day-1 Onboarding**: When installing CountUp on a new phone, the main screen is empty and hides the settings/backup menu entirely. A user migrating from an old device cannot restore their data without first discovering that they must create a throwaway counter to reveal the restore options.
3. **Silent Privacy Leaks on Home Screen Widgets**: When a user deletes a counter that was bound to a home-screen widget, the widget silently switches to display an unrelated counter (including private or hidden counters) instead of informing the user that the target was deleted.
4. **Supply-Chain & Release Signing Hazard**: The build system silently falls back to signing release builds with the Android debug certificate if release credentials are not present, risking accidental publication of debug-signed binaries.
5. **Operational Flaws in Background Updates & Mutation Concurrency**: Rapidly tapping "Save" creates duplicate counters, widget resets drop undo records if process death occurs immediately after reset, unhandled file-provider exceptions crash the activity during backup export, and an error in a single widget provider permanently kills the daily midnight rollover alarm.

## Solution

A cohesive release-hardening and data integrity update that eliminates silent failures, enforces transactional guarantees, protects user data boundaries, and streamlines device migration:

1. **Safe, Transactional Backup & Restore with Strict Schema Versioning**:
   - Backup files declare an explicit schema version. Backups with future, unsupported schema versions are rejected immediately with guidance to update the app.
   - Corrupted or truncated files are explicitly flagged as "Partial Recovery". The "Replace All" strategy is strictly disabled for damaged backups, permitting only non-destructive "Merge".
   - A pre-restore safety snapshot is written to disk prior to any destructive operation, allowing instant rollback in the event of an aborted or failed restore.
   - Preferences and item datasets are committed atomically in a single transaction with a monotonic revision identifier, ensuring self-healing mechanisms compare revisions rather than record counts.
2. **First-Class Restore on Clean Installations**:
   - The initial empty state displays a prominent "Restore from backup" action alongside "New item", allowing new or migrating users to populate their counters immediately upon launch.
3. **Widget Tombstone States for Deleted Milestones**:
   - When a counter explicitly bound to a widget is deleted, the widget displays a calm, clear tombstone state ("Counter removed — tap to reconfigure") rather than silently falling back to arbitrary counters.
4. **Deterministic, Fail-Safe Release Configuration**:
   - The release build configuration requires valid release keystore credentials and leaves release builds unsigned if absent, completely eliminating silent debug-key fallbacks and purging legacy password file references.
5. **Hardened Concurrency, Background Alarms & Stream Operations**:
   - Editor mutations enforce an in-flight saving guard (`isSaving`) to debounce rapid submissions and prevent duplicate items.
   - Storage Access Framework streams are guarded against provider exceptions, closed cleanly, and restricted to a 2 MB size cap.
   - Widget resets and undo records are committed together in a single atomic store operation.
   - The daily midnight alarm isolates each widget family update within individual error boundaries, ensures next-day rescheduling inside a `finally` block, and cancels itself when zero widgets are placed on the home screen.

## User Stories

1. As a habit tracker restoring an old backup, I want the app to reject backup files created by future versions of CountUp, so that incompatible future features do not corrupt my local data.
2. As a user importing a damaged or truncated backup file, I want the app to clearly inform me that only partial data could be recovered, so that I understand the file is incomplete.
3. As a user reviewing a damaged backup, I want the "Replace All" option to be completely disabled, so that I cannot accidentally wipe my entire local collection of counters with a partial recovery.
4. As a user restoring a damaged backup, I want to merge the salvaged counters with my existing items, so that I retain both my local data and whatever items were recovered.
5. As a user who confirms a full restore ("Replace All"), I want the app to create a safety snapshot of my existing data before replacing anything, so that my previous items can be rolled back if the restore is interrupted.
6. As a user upgrading my phone, I want to see a "Restore from backup" button immediately on the initial empty screen, so that I do not have to create a dummy counter just to access the restore menu.
7. As a new user opening CountUp for the first time, I want both "New item" and "Restore from backup" options clearly presented, so that I can choose between starting fresh or migrating an existing file.
8. As a user with a home-screen widget tracking a private milestone, I want the widget to show "Counter removed" if I delete that counter, so that the widget never exposes an unrelated private counter on my home screen.
9. As a widget user whose bound counter was deleted, I want tapping the "Counter removed" widget to open the configuration picker, so that I can easily reassign the widget to a new counter.
10. As a user rapidly double-tapping the "Save" button in the item editor, I want the app to submit only one save operation, so that duplicate counters are never created.
11. As a user saving a counter, I want the save button to indicate a busy state while persisting, so that I know my changes are being written safely.
12. As a user resetting a counter from a home-screen widget, I want the reset and the undo record to be saved together atomically, so that a process termination immediately after tapping reset never destroys my ability to undo.
13. As a user undoing a reset in the app, I want the undo action to verify the item hasn't undergone subsequent edits, so that I do not inadvertently revert newer intentional changes.
14. As a user exporting a backup to an external cloud or document provider, I want the app to display a helpful message if the provider fails to open the file, so that the app does not crash or silently fail.
15. As a user accidentally selecting a massive non-backup file in the file picker, I want the app to reject files larger than 2 MB with a clear notice, so that my device does not run out of memory.
16. As a user with multiple widgets on my home screen, I want a failure in one widget style's update pass not to block other widgets from updating at midnight, so that all working widgets remain accurate.
17. As an energy-conscious user, I want the midnight alarm to reschedule reliably every night even if an error occurs during an update, so that my widget days advance accurately without me having to open the app.
18. As a user who removes all CountUp widgets from the home screen, I want the app to cancel the daily midnight alarm, so that zero background alarms run when no widgets are active.
19. As an open-source user building the project, I want the release build to fail fast or remain unsigned when release keystore credentials are missing, so that I never produce an artifact secretly signed with a debug certificate.
20. As a developer auditing the codebase, I want all legacy references to plain-text keystore password files completely removed from the build scripts, so that credential management follows strict environment variable and local properties standards.
21. As a user restoring a backup, I want appearance settings (sort order, theme, background) and items to be applied in a single transactional write, so that a crash midway through restore cannot leave my app in a mismatched partial state.
22. As an offline user, I want the app's self-healing recovery pipeline to select candidate backups based on monotonic revision timestamps rather than record counts, so that intentionally deleting items does not cause older backups to resurrect deleted entries.

## Implementation Decisions

### 1. Backup Schema Versioning & Sealed Result Pipeline
- The backup parsing engine will yield a sealed result hierarchy representing all validation outcomes:
  ```kotlin
  sealed interface BackupValidationResult {
      data class Valid(val payload: CountUpBackupPayload) : BackupValidationResult
      data class UnsupportedSchema(val detectedVersion: Int, val maxSupportedVersion: Int) : BackupValidationResult
      data class Damaged(val salvagedPayload: CountUpBackupPayload, val recoveredCount: Int) : BackupValidationResult
      data object Corrupted : BackupValidationResult
  }
  ```
  *(Prototype pattern encoding the validation state machine)*
- Files containing `schemaVersion > CURRENT_SCHEMA_VERSION` immediately evaluate to `UnsupportedSchema`.
- Salvaged payloads evaluate to `Damaged`.
- The restore confirmation interface receives this result: when `Damaged` is active, the UI disables the `REPLACE_ALL` strategy option, displays an explicit alert regarding partial recovery, and restricts confirmation to `MERGE_KEEP_EXISTING`.

### 2. Transactional Persistence & Rollback Guarantees
- The storage layer will persist preferences (sort order, theme mode, background theme) and counter items within a single atomic commit pass.
- Persisted snapshots will record a monotonically increasing `revision: Long` counter. When evaluating self-healing candidates following storage faults, candidate priority will be determined strictly by revision order rather than record count, preventing resurrected deletions.
- Prior to executing a `REPLACE_ALL` restore operation, the storage manager writes an ephemeral safety snapshot (`countup_pre_restore_safety.json`). If the replace operation fails at any point, the store automatically reverts to this snapshot.

### 3. Clean-Install Empty State Architecture
- The empty state view will provide two primary visual actions:
  - Primary button: "Create your first counter"
  - Secondary outlined button: "Restore from backup"
- Tapping "Restore from backup" launches the Storage Access Framework document picker directly from the empty state.
- The global settings and backup menu triggers will remain accessible regardless of whether the counter list is empty or populated.

### 4. Widget Target Resolution & Tombstone Representation
- When evaluating a widget instance's target counter:
  - If the widget is unconfigured (no binding assigned), it displays the default prompt or unconfigured state.
  - If the widget is bound to an identifier and that counter exists, it renders normal counter metrics.
  - If the widget is bound to an identifier but the counter **no longer exists** in storage, the reducer produces an explicit `Tombstone` state.
  - In `Tombstone` state, the widget displays "Counter removed" and "Tap to reconfigure", with a launch intent targeting the item selection dialog. The system will never fall back to `items.firstOrNull()` or another arbitrary counter.

### 5. Release Signing Integrity & Build Gating
- In the build configuration, `signingConfig` for release variants will reference only the release signing block (which is null if keystore credentials are not found). The fallback to `signingConfigs.getByName("debug")` is eliminated.
- Release packaging tasks (`assembleRelease`, `bundleRelease`) will execute without silently signing with debug credentials.
- The fallback file lookup targeting `keystore-pass.txt` is completely excised. Only the `COUNTUP_KEYSTORE_PASS` environment variable and `countup.keystore.pass` in `local.properties` remain authorized.

### 6. Mutation Serialization & Concurrency Protection
- The presentation layer state model will introduce an explicit `isSaving: Boolean` property.
- When a save event is received, subsequent save events are ignored while `isSaving` is active, and the editor dialog's positive action is disabled to prevent duplicate submissions.
- Resetting an item from a widget will be consolidated into a single atomic method in the store (`resetWithUndo`), synchronizing the anchor date modification and undo whisper record within one atomic disk operation.

### 7. Document Provider Resilience & Stream Constraints
- Storage Access Framework launchers in the activity will wrap provider operations (`openInputStream`, `openOutputStream`) in comprehensive error handling for `FileNotFoundException`, `SecurityException`, and `IOException`.
- Stream consumption will enforce a strict 2 MB input limit. Payloads exceeding this threshold are aborted with an explicit user notification, preventing OutOfMemory exceptions.

### 8. Midnight Alarm Failure Isolation
- The daily rollover receiver will wrap each widget family's update routine in an independent error-handling boundary.
- Rescheduling the next midnight alarm via `AlarmManager` will execute inside a `finally` block to guarantee continuous scheduling.
- Before scheduling an alarm, the system queries whether any widgets are currently placed. If zero widgets are placed across all providers, any existing midnight alarm is cancelled and no new alarm is registered.

## Testing Decisions

### What Makes a Good Test
Tests must verify externally observable behavior and domain invariants rather than internal implementation details:
- Assert that invalid or future payloads produce the expected user-visible error state and leave storage untouched.
- Assert that partial recovery restricts the user to safe merge strategies.
- Assert that deleting a bound item produces a tombstone state rather than an arbitrary substitution.
- Assert that rapid concurrent save events yield exactly one persisted item.
- Assert that midnight alarm scheduling survives simulated provider crashes.

### Modules Tested
1. **Backup Serialization & Validation**: Valid, unsupported schema, truncated, oversized, and corrupted JSON payloads.
2. **Persistence & Store Engine**: Atomic multi-field commits, pre-restore rollback, monotonic revision selection, and single-pass reset-with-undo.
3. **Presentation & MVI ViewModel**: Debounced save submissions (`isSaving`), restore strategy state transitions, and clean-install empty state event routing.
4. **Widget State Reducer**: Resolution logic for unconfigured, valid, and deleted bindings.
5. **Midnight Alarm Receiver**: Isolated widget provider failure execution and conditional alarm cancellation when zero widgets exist.

### Prior Art
- `CountUpBackupPayloadTest.kt`: Existing tests for JSON decoding, encoding, and salvage parsing.
- `CountUpStoreTest.kt`: Existing unit tests for SharedPreferences and atomic backup file fallback.
- `CountUpViewModelTest.kt`: StateFlow and Turbine tests validating MVI event handling and dialog states.
- `ZenWidgetReducerTest.kt`: Reducer tests validating milestone and display string computations.
- `MidnightAlarmReceiverTest.kt`: Tests for rollover timestamp calculation across month and year boundaries.

## Out of Scope

- Introducing complex third-party database frameworks (Room, SQLDelight) or object mappers.
- Implementing automatic background cloud backup syncing services or proprietary sync backends.
- Adding recurring reminders, notifications, or calendar event integrations.
- Redesigning the core Material 3 / ink-wash visual design language.
- Modifying home-screen widget preview layouts or adding new widget form factors.

## Further Notes

- **Recurring Widget Guardrail Adherence**: All widget updates must preserve existing contracts specified in `docs/RECURRING_ISSUES.md`:
  - Zen Pebble widget (`zen_pebble_widget_info.xml`) must maintain `android:resizeMode="none"` and `android:widgetFeatures="reconfigurable"` (omitting `configuration_optional` so card picker auto-launches on placement).
  - Zero background work: no persistent background services or `WorkManager` instances are permitted.
  - Alarm registration continues using low-power, non-wakeup `AlarmManager.RTC` alarms to maintain zero battery drain during overnight sleep.
